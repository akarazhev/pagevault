# Распространение PageVault и Chrome Web Store

Принята модель: расширение устанавливается из Chrome Web Store, а локальный компонент PageVault — отдельным установщиком для ОС пользователя. Один исполняемый файл обслуживает Native Messaging для браузера и MCP для локального агента. Первым этапом реализован MCP; публикация в магазине и графические установщики остаются следующими этапами.

## Два пакета

Chrome Web Store принимает ZIP с файлами расширения и `manifest.json` в корне. Для него нужны содержимое `extension/`, иконки и скрипты расширения. Полный `PageVault-1.2.0.zip` с каталогом `pagevault/`, исходниками, установщиками и программами для ОС служит отдельным комплектом. Требование к структуре ZIP описано в [подготовке расширения](https://developer.chrome.com/docs/webstore/prepare).

Нативный компонент устанавливается в ОС и регистрирует `com.pagevault.host`. Chrome запускает зарегистрированную программу и связывается с ней через stdin/stdout; механизм описан в [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging). Установка расширения из магазина сама не выполняет эту регистрацию.

Для будущих выпусков нужны отдельные артефакты: небольшой ZIP расширения для магазина и установщики локального компонента на [GitHub Releases](https://github.com/akarazhev/pagevault/releases). Существующий сборщик пока создаёт полный комплект.

## Первый запуск после установки из магазина

Планируемая последовательность:

1. Пользователь устанавливает PageVault из Chrome Web Store.
2. Расширение проверяет связь с `com.pagevault.host`.
3. При отсутствии помощника показывает назначение локального компонента и ссылку на установщик для выбранной ОС/архитектуры.
4. Пользователь скачивает и запускает установщик. Он размещает программу, выбирает или сохраняет SQLite, создаёт `pagevault.json` и регистрирует native-host для ID расширения из магазина.
5. Пользователь возвращается в расширение и нажимает проверку подключения. Интерфейс показывает версию помощника и фактический путь SQLite.
6. Для агента отдельно настраивается запуск этой программы с командой `mcp`.

Расширение не сможет незаметно установить и запустить системную программу; установка компонента остаётся явным действием пользователя. При отказе от установки интерфейс должен объяснять, что сохранение в SQLite недоступно.

На macOS планируется подписанный и нотарифицированный `.pkg`, на Windows — подписанный `.exe` или `.msi`, на Linux — пакет либо проверяемый установочный скрипт. Текущие программы собираются для шести целей, но такая сборка не заменяет проверку установщика на каждой ОС.

## ID и обновления

Сейчас публичный ключ закрепляет ID распакованного расширения `ijkioljfdaaplhaldbdpabckkfcieiee`. До выпуска нужно определить ID магазина и проверить соответствие `manifest.key`, `docs/extension-id.txt`, значения в Go и `allowed_origins` в native-регистрации. Если ID магазина отличается, разработческую сборку следует привязать к его публичному ключу. Смысл поля ключа описан в [документации manifest.key](https://developer.chrome.com/docs/extensions/reference/manifest/key).

Расширение будет обновляться через Chrome Web Store. Для локального компонента нужен собственный процесс: новый установщик либо будущий механизм обновления с проверкой целостности и подписи. Первоначально достаточно ручной установки нового выпуска с сохранением SQLite. Необходимо останавливать использующие бинарный файл процессы браузера и MCP-клиента, особенно в Windows; после обновления клиент запускает новый MCP-процесс.

Версии native-протокола, схемы SQLite и MCP должны иметь явные правила совместимости. Будущий экран подключения должен объяснять несовместимость и давать ссылку на подходящее обновление. Автоматическое обновление расширения не должно требовать немедленной несовместимой миграции архива.

## Подготовка к публикации

Понадобятся учётная запись разработчика, регистрационный взнос, описание единого назначения, изображения, контакты поддержки и материалы для проверки. Регистрация описана в [Chrome Web Store](https://developer.chrome.com/docs/webstore/register), процедура — в [инструкции публикации](https://developer.chrome.com/docs/webstore/publish). Решение о допуске принимает проверка магазина.

Назначение PageVault — сохранять выбранные пользователем страницы в личный локальный архив и давать доступ к нему. Для разрешений `nativeMessaging`, `scripting`, `storage`, `alarms`, `unlimitedStorage` и опционального доступа к сайтам нужно объяснить конкретное применение. Проверяющему следует предоставить доступный установщик, порядок проверки и тестовые страницы без личных учётных данных.

Нужны опубликованная политика приватности и согласованные сведения в карточке магазина. [Правила Chrome Web Store](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq) требуют раскрывать обработку данных и при локальном хранении. Политика должна описывать URL, текст, метаданные и опциональный HTML; выбор сайтов пользователем; SQLite и очередь IndexedDB; удаление; отсутствие передачи самим PageVault; отдельный доступ MCP-клиента. Использование облачной модели агентом следует отличать от полностью локальной обработки.

Порядок следующих работ: стабилизировать MCP на реальных сценариях агента, подготовить установщики и экран подключения, согласовать ID и совместимость, опубликовать политику приватности, затем подготовить пакет расширения и отправить его на проверку.
